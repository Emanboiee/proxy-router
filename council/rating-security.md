RATING: 8.2/10 — No P0/P1 security defect: loopback binding, CONNECT target, timeout bounding, record hygiene and the status fast path are all sound; deployable with a few hardening gaps.

FINDINGS:

1. P2 — Hardcoded CONNECT target can false-dead a healthy tunnel and drive the fail-open-to-direct path (IP-leak / routing bypass). `provider_lifecycle.py:313` hardcodes `socks_connect_result(host, port, "example.com", 443, ...)`. In `router.py:2279-2282`, any non-zero REP makes `recover_routed` return a record and `check_egress_live` short-circuits to `("dead", record)` — the authoritative HTTP probe (`probe_url_for` / `probe_egress`) never runs. A proxy that legitimately routes only its configured domains, or an exit from which `example.com` is unreachable/blocked, is marked dead on the strength of one fixed external host. That verdict feeds rotation/failover (`_check_active_fallback`, the provider probe loop in `router.py:6052/6125/6228`) and `_degraded_lanes` already reports such a lane as "failing open to direct" (`router.py:5562`). For a proxy-router whose job is to force domains through the exit, a false dead that flips a configured proxy to direct exposes the client IP. Suggested fix: derive the CONNECT target from the provider's configured probe/routed domain (or probe more than one target and require a majority failure before dead-marking), and never let a single hardcoded external destination be the sole liveness authority for a proxy lane.

2. P3 — `socks_connect_result` does not self-enforce loopback on `host` (defense-in-depth gap; no current exploit). `provider_lifecycle.py:73-108` connects to whatever `host:port` it is given. The only production caller passes `proxy_upstream` (`router.py:2280`), which validates host against `127.0.0.1`/`::1` (`router.py:280-285`), so there is no SSRF today. But the function is a generic network primitive; any future caller fed a config-derived host would bypass the loopback guarantee that the whole proxy-provider model relies on. Suggested fix: validate `host` inside `socks_connect_result` (reject anything not loopback) so the invariant is local to the primitive rather than dependent on every caller.

3. P3 — CONNECT-failure record overwrites the entire egress record, dropping cooldown/quota/block markers. `provider_lifecycle.py:315-322` builds a minimal record (`ok, checked_at, socks_connect_ok, error, socks_connect_code`) and `router.py:1241 -> 1234` writes it via `write_egress`, which replaces the file rather than merging. On a CONNECT rejection this discards `blocked`, `exhausted`, `exhausted_until`, `quota_until`, `fails`, `last_ok_at`, `upstream_error`, etc. A quota-exhausted or operator-blocked proxy lane can be handed back to the selector as eligible, routing traffic through a known-bad exit. `record_egress` (`router.py:1244+`) already does the correct merge. Suggested fix: read the existing record and merge the CONNECT fields into it (same pattern as `record_egress`) instead of replacing it.

4. P3 — Single-shot `recv()` on greeting and CONNECT reply yields false rejections on short/fragmented reads. `provider_lifecycle.py:101` (`recv(2)`) and `:111` (`recv(4)`) assume the full fixed prefix arrives in one syscall. A SOCKS server that splits the greeting or reply across TCP segments produces "socks greeting rejected" / "short CONNECT reply", i.e. a false dead verdict with the fail-open consequence in finding 1. Suggested fix: loop until the expected byte count is read or the shared deadline expires.

5. P3 — Connection-target validation is partial. `provider_lifecycle.py:104` validates `len(host_b) <= 255` and port range but only via `int(target_port)` — an unvalidated non-numeric target would raise an uncaught `ValueError` outside the `(OSError, StartupError)` handler at `:124`. Not reachable in production (target is the literal `"example.com", 443`), but cheap to harden: coerce and validate target_port once at function entry, inside the guarded path.

6. P3 (base issue, one line) — The pre-existing startup-failure record echoes the configured value (`provider_lifecycle.py:309`, `{"detail": f"provider startup failed: {exc}"}`) when `proxy_upstream` raises; unchanged by this PR, noted only because the new code path keeps returning it to status consumers.

SECURITY CONTROLS VERIFIED (evidence, not findings):
- Loopback binding: production upstream is `proxy_upstream`, which rejects non-loopback hosts (`router.py:280-285`); the new probe inherits it.
- No CONNECT SSRF: target is the hardcoded literal `example.com:443` with IDNA/length/port validation (`provider_lifecycle.py:100-104`); no user-controlled destination in any reachable call site.
- Bounded timeouts / blackhole safety: one monotonic deadline shared by connect/send/recv (`provider_lifecycle.py:90, 94, 108, 111`); deadline exhaustion raises `StartupError` from `_remaining` (`:127-131`) and is caught at `:124`. `tests/test_socks_connect_health.py::test_blackhole_is_bounded` passes; full file: 13 passed in 3.17s.
- No secret/target leakage: error strings are static or exception *type names* only (`provider_lifecycle.py:125`), the greeting sends no auth (`b"\x05\x01\x00"`, `:95`), the CONNECT target is not stored, and records are written 0o600 via `write_egress` (`router.py:1234`).
- No new probe on status fast path: `_degraded_lanes` (`router.py:5551-5574`) and `build_provider_status` (`status_snapshot.py:132-179`) only read persisted records; the CONNECT probe lives solely in `recover_routed <- check_egress_live`, which is not reached by `status` / `status --json`.
- Routing gate unchanged: new `fresh_failure`/`usable_evidence` (`egress.py:188,215`) are used only in status reporting (`router.py:5573`); the #219 fallback gate still uses `exit_unusable`, preserving its fail-open-on-absence contract.

TOP_3_TO_9_5:
1. Replace the single hardcoded `example.com:443` CONNECT target with the provider's configured probe/routed domain (or a multi-target majority rule) so a false rejection cannot dead-mark a working tunnel and trigger the direct fail-open path (fixes P2, the only deployment-blocking security concern).
2. Make `socks_connect_result` self-validate loopback `host` and merge CONNECT results into the existing egress record instead of overwriting it (fixes P2-adjacent P3s 2 and 3 — contains SSRF surface and preserves quota/block state).
3. Harden the wire read/validation: loop `recv()` until the full greeting/reply prefix is read within the deadline and validate `target_port` at entry (fixes P3s 4 and 5, eliminating fragmentation-induced false-dead verdicts).
