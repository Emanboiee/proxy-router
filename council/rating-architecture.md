RATING: 6.5/10 — #219/status separation is clean and no global state is added, but the CONNECT-failure write path breaks egress-record write discipline and router.py sits exactly on the 8400-line cap.

FINDINGS:

1. [P1] Two write paths to the same egress key with incompatible merge semantics — `provider_lifecycle.py:313-322` vs `router.py:1244-1251`. `recover_routed` builds a fresh minimal dict (`{ok: False, checked_at, socks_connect_ok: False, error, [socks_connect_code]}`) and hands it to `write_record`; `_write_proxy_egress` (router.py:1241) forwards it to `write_egress` → `state.write_json` (router.py:1234-1238, state.py:75-79), which is a full `json.dumps` replace, not a merge. The healthy path `record_egress` (router.py:1251) does `read_egress` → mutate → write. So a CONNECT rejection atomically erases every other field in `state/egress/<name>/socks.json`: `exhausted`/`exhausted_until`/`quota_until`, `fails`, `tls_fails`/`tls_target`, `last_ok_at`, `latency_ms`, `status`, `blocked*`, `dns_ok`, and any prior `socks_connect_code`. Concrete impact: erasing the quota marker makes `provider_quota_exhausted` (router.py:1357) read a quota-blocked proxy as not exhausted (`quota_active` now False, record fresh so `quota_unknown` False); a concurrent/earlier `record_egress(ok=True)` update can be clobbered by a later rejection write. Why it matters: two writers to one state key with different merge rules → state can regress and the #219 quota gate can be fooled. Suggested fix: keep the leaf pure — pass only changed fields from `recover_routed`, and make the router-side adapter do read-merge-write (`existing = read_egress(name, proxy_profile_key(name)); existing.update(fields); write_egress(...)`) so no field is silently dropped.

2. [P2] Read-side override compensates for a stale persisted flag instead of fixing the write — `egress.py:205-207`. `fresh_failure` special-cases `record.get("ok") is True` to neutralize a lingering `socks_connect_ok=False`, because `record_egress(ok=True)` (router.py:1267+) never clears that flag. Persisted state is left self-contradictory (`ok=true`, `socks_connect_ok=false`) and every future reader must remember the override. Why it matters: correctness depends on a convention known only to `fresh_failure`; a new reader of the record will misjudge health. Suggested fix: clear `socks_connect_ok`/`socks_connect_code` in `record_egress` when `ok is True`, then keep the `fresh_failure` guard only as defense-in-depth for pre-existing records.

3. [P2] `degraded_detail` does not mirror `fresh_failure`'s `ok is True` override — `egress.py:238-241` vs `egress.py:205-207`. A stale record with `ok=True` and a leftover `socks_connect_ok=False` is degraded for staleness (`usable_evidence` False via `exit_unusable`), but `degraded_detail` checks the CONNECT flag before freshness and reports "socks connect rejected (rep=...)". This state is reachable: CONNECT rejection → successful HTTP probe via `record_egress(ok=True)` (flag left set) → no further probe past `ok_window`. Why it matters: the status line attributes degradation to the wrong cause, misleading operators triaging a top-priority health feature. Suggested fix: apply the same `record.get("ok") is True` guard before honoring `socks_connect_ok` in `degraded_detail`, or have `degraded_detail` derive its reason from the same predicate order as `fresh_failure`.

4. [P2] Hard-coded CONNECT probe target and added latency on the live-check path — `provider_lifecycle.py:313`. Every `check_egress_live` for a proxy provider (router.py:2280) now performs a real SOCKS CONNECT to a fixed `example.com:443` with a 0.8s budget before any HTTP probe. The target is unrelated to configured routes: a proxy that allowlists only internal destinations is falsely "dead"; one that permits example.com but blocks real targets is falsely healthy. Why it matters: verdict accuracy depends on an arbitrary external host, and the per-provider latency stacks on status/probe/rotation paths. Suggested fix: derive the CONNECT target from `probe_url_for(name)` or route config, expose target/timeout in config, and probe CONNECT only when the cheap greeting + HTTP result is inconclusive.

5. [P3] router.py is exactly at the cap — 8400 lines (cap 8400, confirmed with trailing newline). The PR is net +1 line (`_write_proxy_egress` helper at `router.py:1241`; `_degraded_lanes` is net -2 at `router.py:5573-5574`), consuming all remaining headroom. Why it matters: compliant today, but the next edit to router.py breaks the cap with no warning. Suggested fix: express the adapter as a `functools.partial` or inline lambda at the call site (router.py:2280) instead of a module-level one-line def, restoring a couple of lines of margin.

6. [P3] Leaf boundary: egress-record schema duplicated in the lifecycle leaf — `provider_lifecycle.py:314-319` hard-codes field names (`socks_connect_ok`, `socks_connect_code`, `checked_at`) that `egress.py:238-240` later reads. No shared constant; a rename in one file silently disables detection. Why it matters: schema drift across module boundaries with no compile-time guard. Suggested fix: define the field-name constants in `egress.py` (which imports neither `provider_lifecycle` nor `router`, so no cycle) and import them where the record is built.

7. [P3] Duplicated SOCKS greeting logic — `provider_lifecycle.py:55-70` (`socks_ready`) and `:73+` (`socks_connect_result`) both send `b"\x05\x01\x00"` and compare `== b"\x05\x00"`. Why it matters: minor maintainability cost (subtract-before-add) — two places to update if the greeting changes. Suggested fix: extract a shared `_socks_greeting(connection, deadline)` helper. Not a deploy blocker.
