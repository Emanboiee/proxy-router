RATING: 5.5/10 — Detection logic is sound and all 121 related tests pass, but a CONNECT rejection clobbers durable quota/block state and stale connect evidence is never cleared, so this is not deployable as-is.

FINDINGS:

1. P1 — CONNECT rejection overwrites the whole egress record, silently dropping quota/block markers
   - `provider_lifecycle.py:314-320` builds a fresh minimal dict (`ok/checked_at/socks_connect_ok/error[/code]`) and passes it to `write_record`; `router.py:1241` maps that to `write_egress` → `state.write_json` (`state.py:67-80`), which serializes the value wholesale (overwrite, not merge — unlike `record_egress` at `router.py:1251`).
   - Every other field is lost: `exhausted`/`exhausted_until`/`quota_until`, `blocked`/`blocked_until`/`block_reason`, `last_ok_at`, `fails`, `latency_ms`, `dns_ok`, `tls_fails`, `upstream_error`.
   - Why it matters: `_apply_upstream_failure` (`router.py:2521-2524`) sets an unexpired `exhausted`/`exhausted_until` marker on proxy providers (synthetic `socks.conf` key, `router.py:1347`). A single transient CONNECT rejection clears that marker; `provider_quota_exhausted` (`router.py:1357`) then reads false and the fallback reinstatement gate at `router.py:1490` no longer blocks restoring the quota-blocked exit. After the proxy recovers (`ok=true` written), the quota block is gone permanently, so the exit serves traffic again before its reset — re-triggering the 429/exhaustion the marker existed to prevent. It also creates a lost-update race with the keepalive writer (`router.py:2141`) that merges into the same file.
   - Suggested fix: have `recover_routed` update via `read_egress`-then-merge (or call a shared merge helper) so only health fields are replaced; preserve all marker fields. Add a regression test that sets `exhausted_until` in the future, triggers a rejection record, and asserts `provider_quota_exhausted()` is still True.

2. P2 — The ok=true-clears-connect-flag fix is partial: `degraded_detail` still reports a stale rejection indefinitely
   - `egress.py:205-206` correctly returns False from `fresh_failure` when `ok is True`, and `usable_evidence` (`egress.py:225`) therefore un-degrades a recovered lane. But `degraded_detail` (`egress.py:238-240`) checks `record.get("socks_connect_ok") is False` with neither the `ok is True` override nor any freshness check on the connect flag, and `record_egress` (`router.py:1267-1284`) never clears the flag on success.
   - Confirmed at this head: after `ok=true` recovery the record `{ok:true, checked_at:now, socks_connect_ok:false, socks_connect_code:5}` reads `usable_evidence=True` (correct), but a later transient HTTP failure with the same stale flag yields `degraded_detail == "socks connect rejected (rep=5)"` — the CONNECT actually succeeded. An aged-out record (`checked_at` 90k old) also still says "socks connect rejected (rep=5)" instead of "stale or unknown".
   - Why it matters: operators get a false, sticky CONNECT alarm and chase the wrong root cause; the status detail contradicts the health verdict. The task's explicit "ok=true-clears-connect-flag fix" is therefore incomplete — it clears the verdict, not the persisted evidence or the detail.
   - Suggested fix: clear `socks_connect_ok`/`socks_connect_code` (and stamp a `socks_connect_checked_at`) inside `record_egress` when `ok=True`, and apply the same `ok is True` override at the top of `degraded_detail` so a stale flag can never win priority.

3. P2 — Hardcoded CONNECT target + 0.8s budget + early return produce false "dead" verdicts
   - `provider_lifecycle.py:313` always probes `example.com:443` with `timeout=0.8`, and `router.py:2279-2282` returns `"dead"` immediately on any CONNECT rejection, skipping the HTTP probe at `router.py:2286` that would actually prove the exit carries the configured traffic.
   - Why it matters: the router's own outbound (`router.py:3274-3280`) has no fixed destination and real routes target user domains (discord/x.com/school-warp). A proxy with a destination allowlist, or one whose DNS/TCP to example.com is slow, is fully usable for routed traffic yet is marked dead — and the corroborating HTTP probe never runs. 0.8s is tight for a remote proxy to resolve and open a fresh outbound TCP connection; there is no retry, unlike the HTTP path's 2s re-probe (`router.py:2287-2292`). A single transient failure writes `socks_connect_ok=false` and flips `egress_probe`'s `ok` to false (`router.py:6146`), which automation may act on.
   - Suggested fix: derive the CONNECT target from `probe_url_for(name)` (or make it configurable), raise the timeout and add one bounded retry, and cap the CONNECT-only outcome at `"degraded"` — let the HTTP probe confirm before declaring `"dead"` (`router.py:2281-2282`).

4. P3 — Partial `recv` yields false "greeting rejected" / "short reply" on fragmented replies
   - `provider_lifecycle.py:95-98` uses `connection.recv(2)` for the greeting and `provider_lifecycle.py:111-114` uses `recv(4)` then requires `len >= 2` for the CONNECT reply. TCP `recv` may return fewer bytes than requested; a proxy that writes the greeting or reply header across two segments can return 1 byte and be misclassified as a rejection. The `FakeSocks` fixture (`tests/test_socks_connect_health.py:51,62`) sends each reply in one `sendall`, so fragmentation is untested.
   - Suggested fix: loop until N bytes are read or the shared deadline expires (a `recv_exact` helper), then classify.

5. P3 — CONNECT-rejection record shape loses the `rep=` reason in `egress probe` output
   - `recover_routed` startup failures return `{"detail":..., "dns_ok":None}` (`provider_lifecycle.py:312`) while rejection returns `{"ok":False,...,"error":...}` (`provider_lifecycle.py:315-318`); neither carries `status`. `egress_probe._check_one` (`router.py:6146-6154`) derives detail only from `record["status"]`/`record["dns_ok"]`, so a `"dead"` CONNECT rejection prints the generic "probe connection" — the `rep=5` the new code captures never reaches probe JSON (it only appears via `_degraded_lanes`). Startup-failure dicts are also not persisted at all, so `status` and `egress probe` can disagree.
   - Suggested fix: give the failure record the same shape as `record_egress` outputs (include `status`/a machine-readable reason) and persist it consistently; have `_check_one` surface `socks_connect_code`/`error`.

TOP_3_TO_9_5:
1. Stop clobbering: make `recover_routed`'s write a merge that preserves `exhausted`/`quota_until`/`blocked`/`last_ok_at`/`fails` (mirror `record_egress`, `router.py:1251`), with a test proving an active quota block survives a rejection.
2. Finish the ok=true fix: clear `socks_connect_ok`/`socks_connect_code` in `record_egress` on success and apply the same override in `degraded_detail` (`egress.py:238`), so stale connect evidence cannot survive or misreport.
3. Remove the false-positive path: target the provider's real probe destination (not hardcoded example.com), raise/retry the 0.8s budget, and require HTTP corroboration before `"dead"` instead of early-returning (`router.py:2279-2282`).
